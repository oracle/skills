# Runtime Error Catalog: Passes Validate/Import, Fails at Runtime

## Overview

`apex validate -input` and `apex import -input` prove a generated app **compiles and imports**. They do not prove the app **behaves correctly when a user interacts with it**. A specific class of APEX defects is invisible to the compiler and importer but breaks the first time a user submits a page, saves an editable grid, fires a cascading LOV, or hits an error path.

Use this catalog when a page that validated and imported cleanly then fails at runtime with one of the signatures below. It complements `references/domains/debugging/failure-map.md` (symptom to owning layer) by giving the **root cause** (documented where Oracle documents it, marked observed otherwise) and a **generation-time rule** that prevents each defect, so a generator can avoid emitting the defective shape in the first place.

Each entry lists the runtime signature, the cause, the generation-time prevention rule, and how to confirm at runtime. Where a specific error string or global is **not** in official Oracle documentation, it is marked as such — the underlying mechanism is documented even when the surfaced code is community terminology.

## 1. Full-page submit rejected for a display-only or protected item

- **Runtime signature:** A full-page submit fails in the APEX **accept phase**, before any validation or process runs. The surfaced code is commonly `WWV_FLOW.ITEM_POSTING_VIOLATION` (community terminology), with a backtrace through the page-item accept/parse internals, naming a display-only or read-only item on the page.
- **Cause:** APEX enforces **Page Protection**. A page protection violation "may be caused by manual alteration of protected page items" — APEX rejects a submitted page item whose posted value it did not expect to receive. APEX does not expect a **Display Only** item to post a value on a full-page submit (it does not render as a submitting form field), so if one posts a value anyway, the accept phase rejects it. Separately — and as a distinct mechanism in a later phase — a Display Only item whose *Save State* is **No** is excluded from **Automatic Row Processing DML** (documented Changed Behavior, compatibility mode 4.1); that rule governs only whether the item's value is *written* during row processing, not the accept-phase rejection. The specific string `ITEM_POSTING_VIOLATION` is not in the Oracle Error Messages reference, but the Page Protection mechanism behind it is documented (see Sources).
- **Generation rule:** Never let a display-only item post a value on a full-page submit. Render the visible value as **static region content** (or a normal read-only item that does not submit), and carry any value the page must post in a **hidden item**. Keep that hidden item **Value Protected** (the default) so moving the value off the display-only item does not weaken tamper protection; only turn Value Protected off when the item must be client-set, and then never trust it for a security or authorization decision — validate it server-side. When only a few fields are mutable, submit them through an AJAX action instead of a full-page submit.
- **Related silent variant (observed):** An item that is **read-only at accept time** — including one made read-only *conditionally* — does not post an editable value, so if nothing else populates it the save can receive null for that item, with no error raised (the field still shows its rendered value). Do not gate a submittable value behind a read-only-when condition; mirror it into an always-writable hidden item and read that on save. (An always-writable hidden item has Value Protected off, so keep such shadow items to non-sensitive values and validate them server-side.)
- **Runtime confirmation:** Reproduce the full-page submit with APEX debug on. A backtrace showing the failure in the **accept / item-parse phase** (not inside a validation or process) confirms Page Protection rejection. For the silent-discard variant there is no error — confirm by checking that the value never reached the database.

## 2. Legitimate AJAX submit rejected by Session State Protection

- **Runtime signature:** An AJAX item-submit — a cascading LOV, an in-grid edit, a partial submit — fails after import, often surfacing `ORA-20987`.
- **Cause:** **Session State Protection (SSP)** appends checksums to protect page items from URL/value tampering. Item protection levels are *Unrestricted*, *Checksum Required* (Application/User/Session Level), and *Restricted*. An item the **user edits and submits interactively** set to *Checksum Required* is rejected when the client posts it, because that level is intended for values the application sets, not for user-editable input. **On the error number:** `ORA-20987` is **not** in the Oracle Database Error Messages reference — it is a generic `raise_application_error` number that Oracle reuses for several unrelated APEX conditions (for example APEX_JSON parse errors and certain task-operation errors), so the number alone is not a session-state-protection signature. Treat it as a hint and confirm from the actual message and the failing call; the **SSP mechanism** is the documented root cause in this entry's scenario.
- **Generation rule:** Match the protection to the channel — the levels are not interchangeable. Set items the user edits and submits via **AJAX or a form** to **Unrestricted**. Use **Checksum Required** only for values that arrive through a checksum-bearing URL, and **Restricted (may not be set from browser)** for non-data-entry values set only server-side. For a hidden item whose value must round-trip unchanged, use its separate **Value Protected** attribute rather than a Restricted level. Do not place a display-only item on a page and then full-page-submit it (see entry 1) — convert it to a hidden item (kept Value Protected unless it must be client-set).
- **Runtime confirmation:** Fire the AJAX action live (trigger the cascade, save the in-grid edit) and confirm it completes with no checksum/`ORA-20987` error. Because the number is overloaded, read the actual message and the failing call to confirm it is an SSP/checksum rejection and not one of the other -20987 conditions.

## 3. ORA-22816 on editable-grid insert (RETURNING through an INSTEAD OF trigger view)

- **Runtime signature:** Inserting a row in an editable Interactive Grid raises **ORA-22816**.
- **Cause:** The native Interactive Grid DML process with **"Return Primary Key after Insert"** issues `INSERT … RETURNING` against the grid's source. When that source is a **view with an INSTEAD OF trigger**, `RETURNING` is not supported: the Oracle Error Messages reference states ORA-22816 occurs because the RETURNING clause is not supported for, among others, **INSTEAD OF triggers**, and directs you to "use a separate SELECT statement to retrieve the values."
- **Generation rule:** Do not use native IG DML with *Return Primary Key after Insert* when the region's source is a view carrying INSTEAD OF triggers. Replace the native IG DML with a **custom process bound to the editable region** that branches on `:APEX$ROW_STATUS` and obtains any generated key **without a `RETURNING` clause** (assign it into a bind variable directly). The grid can keep its view as the source; you do not have to re-source it to the base table, though dropping derived/display-only columns is one way to simplify the write. Binding the process to the region is what makes it run once per submitted row.
- **Runtime confirmation:** Insert a row via the grid's Save. After converting to the region-bound process, confirm `:APEX$ROW_STATUS` is populated per submitted row and the key is set via the manual assignment. (A process that is not bound to the editable region does not receive per-row `:APEX$ROW_STATUS` values, so its row branching will not fire as intended.)

## 4. Editable Interactive Grid save returns HTTP 400 (Reload on Submit)

- **Runtime signature:** Saving an editable Interactive Grid (often inside a modal) returns **HTTP 400** from ORDS with a message stating that, for an editable Interactive Grid, the page attribute **"Reload on Submit" must be set to "Only for Success."**
- **Cause:** In practice, a page hosting an editable Interactive Grid requires the page-level **Reload on Submit = Only for Success** — under another setting the Save returns the HTTP 400 above and the grid will not save (community/observed; the HTTP 400 hard requirement is **not** stated in Oracle documentation). What Oracle *does* document, in the Accessibility Guide, is the **recommendation** to use "Only for Success" for accessible error handling: errors render on the client without a full page reload, and on error screen-reader users are notified via an ARIA `alert` role rather than waiting for a reload.
- **Generation rule:** Whenever a page contains an editable Interactive Grid, set the page's **Reload on Submit** to **Only for Success**. Make it a build-time invariant tied to "page has an editable IG," not a value copied from another page.
- **Runtime confirmation:** Save the grid (especially in a modal) and confirm no HTTP 400. This defect is **distinct** from ORA-22816 (entry 3) — a page-attribute misconfiguration, not a DML/trigger issue.

## 5. A failed operation shows a green success message (error routed through the success path)

- **Runtime signature:** An operation fails server-side but the user sees a **green success message**, and any close/branch behavior tied to "success" still runs.
- **Cause:** APEX's success-message channel renders as **success unconditionally** — it has no notion of whether the operation actually succeeded. If error-handling code routes a genuine failure through that channel (or swallows a raised exception so the page still branches to the success reload), the failure is displayed as success. The **documented** correct path for a processing error is `APEX_ERROR.ADD_ERROR`, which adds the error to APEX's error stack for display inline in a notification or on the error page. (The PL/SQL global commonly used to set a success banner, `apex_application.g_print_success_message`, is **not** in the official APEX API reference; anchor generated code on the documented `APEX_ERROR` API and on raised validations rather than relying on that global.)
- **Generation rule:** Never signal a failure through a success channel. Route genuine failures through **`apex_error.add_error(..., p_display_location => apex_error.c_inline_in_notification)`** — added in a page validation or raised in an after-submit process — so the error surfaces inline and the page does not proceed to the success reload. (The precise halt/no-reload behavior depends on where in the after-submit sequence the error is added and on the app's compatibility mode, so add it before the success branch.) Do not also set whatever flag triggers the success reload, and let a raised exception propagate rather than swallowing it in a `WHEN OTHERS` that lets the page "succeed" and close. Reserve the success-message reload strictly for the confirmed-OK branch.
- **Runtime confirmation:** Force the failure path live: the message must render **as an error** and the page should **stop before** its success reload/close. A green success message or a completed close on a forced failure means the error was mis-routed through the success path. Never treat the message as proof of a write — confirm the actual row change in the database (observed: a stale `success_msg` URL parameter can also replay a prior success banner when nothing changed).

## Version Notes

- Session State Protection, Page Protection, and the Reload on Submit attribute are stable, documented APEX features across current releases (verified against APEX 23.1–24.2 documentation; see Sources).
- The exclusion of **Display Only** items with *Save State = No* from Automatic Row Processing DML is documented as a Changed Behavior under **compatibility mode 4.1**; apps running an older compatibility mode can differ.
- ORA-22816 is an Oracle Database error and is independent of APEX version.
